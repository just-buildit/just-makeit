- **A binding fragment a removed member left behind is reported, and a re-add over it is refused (gh-1983, gh-2461).** `jm remove object` on a module object left its `<module>_ext_<obj>.c` fragment in older jm versions, and `jm status --check` called the tree clean. Adding an object of that name again kept the stale fragment, which still called the old object's C, so the build failed with an implicit declaration. `jm remove` has deleted the fragment since gh-2516. Now `jm status` reports a fragment that no member owns and nothing includes as `ORPHAN`, which fails `--check` and is listed under `orphan_fragments` in `--json`. `jm object --module` and `jm view` refuse to add a member over such a file, naming it, until you delete it. A view whose lowercased class name is an object of its module (a view `Frame` over an object `frame` whose class was renamed) shared that object's fragment file, which the aggregator then included twice, so the build failed. That view is now refused when the manifest is loaded or saved.
