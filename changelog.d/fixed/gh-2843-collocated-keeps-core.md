- **A module's collocated object keeps what the module's core held (gh-2843).** `jm object m --module m` rendered the object's `m_core.h` and `m_core.c` over the module's own: a module function declared before the object lost its declaration (`m_ext.c` then called a function nothing declared, and `jm status --check` reported the header STALE), and any function you had written into `m_core.c` was gone with no prompt. Worse, `jm regenerate`, `jm add --force` and `jm remove state --force` on that object deleted the module's whole `native/src/m/` directory, taking a module function's hand-written `<fn>.c` body and your own code in `m_core.c` with it, on exit 0. Now the object's rebuild replaces only the object's own code in the shared core: what it renders wins for the names it declares, the previous object's stale accessors go, and everything else in the files is kept whole, with its comments: a module function's declaration and body (also under `--discard`, which discards the object's bodies, not the module's), your helpers, macros, typedefs and `#include`s. Adding the object back after `jm remove object` keeps the kept core, and is refused with the definitions named when the core still holds the previous object's code with another signature. A module function's documentation survives too, in the header and in the `.pyi` docstring derived from it, and a kept definition reformatted onto one line (as LLVM and Google styles write it) is not mistaken for another signature. A conditional block (`#ifdef ...`) cannot be carried: in the collocated object's core it is refused with the file named, and `jm regenerate` without `--discard` now refuses to drop one from any object's core rather than losing it silently. The tree is left as it was; move the block, with what it guards, to a file of your own (a header you include, or a `.c` your CMakeLists compiles), or pass `--discard`.
