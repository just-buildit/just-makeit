# stale_project example

**Upgrading a project an old just-makeit generated.** `tree/` is a real
project, generated by just-makeit **0.33.14** and never touched since except
by its author, who wrote a kernel into it. This example upgrades it to the
jm you are running, one step at a time, and proves the result: `jm status
--check` clean, built, tested, the author's code intact, and a bug the old
version shipped now fixed.

Use it as the recipe for your own project. Every step below is the same
command you would run, and the order matters.

## TL;DR — see it work first

```sh
just-makeit example stale_project
# stale_project: OK
```

## What you start with

A project with a standalone object (`gain`), a module `dsp` holding an
object `fir` with a variable-output method, an array method, a writable
property and a module function — the shapes a real library has. `FREEZE.toml`
records the exact commands that made it.

Its author changed one thing jm generated: the body of `fir_step` in the
sacred header `native/inc/fir/fir_core.h`.

```c
return x * state->scale;
```

An upgrade must leave that alone, and this one does.

## 1. Read before you write

```sh
jm status
```

It exits 1 and sorts what is behind into kinds, each with what to do about
it: files the manifest implies that are **missing** or **stale**, a binding
fragment that is **unreconciled**, create-only files that are **outdated**,
and C cores that are **unwired** from the C library. Keep this output — every
step below answers one of its sections.

## 2. `jm apply`

```sh
jm apply
```

It writes everything the manifest implies that is missing and reconciles the
wiring jm owns, then stamps `just-makeit.toml` with the version you ran. It
also warns, loudly, about the fragment it will not rewrite:

```
warning ~: native/src/dsp/dsp_ext_fir.c: binding no longer matches the
manifest [steps: jm's out= guard tests C-contiguity and this fragment does
not, so a strided out= is filled through a copy and silently ignored; ...]
```

That is a real bug, and the example shows it in running code: built at this
point, `fir.steps(x, out=every_other_element)` returns normally and leaves
the caller's buffer untouched.

### 2b. The root `CMakeLists.txt`, which jm maintains only in part

`apply` keeps the root `CMakeLists.txt`'s marked blocks current (the
components, modules and external dependencies) and never touches the rest,
and `jm status` does not yet compare the rest either
([gh-1471](https://github.com/just-buildit/just-makeit/issues/1471)). So
every fix to that template since your project was generated is missing,
silently. Among them are the Windows ones: without them this project does not
build under clang-cl (`ninja: error: multiple rules generate stale.lib`).

Get today's version from a scratch project of the same name, merge it into
yours, and let `apply` put the managed blocks back:

```sh
(cd /tmp && jm new stale)
diff /tmp/stale/CMakeLists.txt CMakeLists.txt    # merge what you want
cp /tmp/stale/CMakeLists.txt CMakeLists.txt      # here: never edited, so whole
jm apply
```

If you added your own targets to it, merge by hand instead of copying — or
move them to a `native/src/<dir>/<dir>_extra.cmake`, which jm includes and
never writes.

## 3. `jm upgrade`

```sh
jm upgrade
```

Runs the migrations the schema carries. For this project it respells
`complex` to `_Complex` in four files — the same type and ABI — which goes
together with adopting the new `clib_common.h` in step 5: both or neither.
See [Upgrading](../upgrading.md).

## 4. Receive the fix the binding fragment is missing

A module object's binding fragment (`<mod>_ext_<obj>.c`) is **sacred** by
default: `apply` only ever *adds* members to it, so a fix to a member it
already has never arrives. Ask which parts differ from today's render:

```sh
jm adopt --check
#   needs acknowledgement fir
#       native/src/dsp/dsp_ext_fir.c
#         differs:   fn:Fir_steps
#         ...
```

jm cannot tell a hand-written body from a render that predates a fix, so it
asks. **Look at the diff.** Here nobody wrote code in that file, so take
today's render — delete it and apply:

```sh
rm native/src/dsp/dsp_ext_fir.c
jm apply
jm adopt --check
#   would flip           fir
```

Then make it jm's for good, so the next fix to a wrapper arrives on the next
`apply` by itself. Under the `[fir]` table in `objects/fir.toml`:

```toml
[fir]
fragment = "generated"
```

Put it **under `[fir]`**, not at the end of the file: appended, it lands in
the last `[[fir.properties]]` table, and jm tells you it has no effect there.
Run `jm apply` once more. If you *had* written code in the fragment, move it
to `dsp_ext_fir_extra.c` beside it first — jm includes that file and never
writes it. See
[Who owns a module's binding fragment](../configuration.md#who-owns-a-modules-binding-fragment).

## 5. Adopt the create-only files jm ships newer

`jm status` lists them as `OUTDATED`: `.gitignore`, `Makefile`, `Doxyfile`,
`cmake/stale.pc.in`, `jm_bench.h`, `clib_common.h`. `apply` never rewrites a
create-only file, because your edits may be in it. **Diff each first.** None
was edited here, so each takes jm's render the same way — delete it, and
`apply` writes today's:

```sh
rm .gitignore Makefile Doxyfile cmake/stale.pc.in \
   native/benchmarks/jm_bench.h native/inc/clib_common.h
rm jb.toml          # renamed bootstrap.toml; step 2 created the new one
jm apply
```

A file you *did* edit: merge jm's version into yours by hand instead.

## 6. Prove it

```sh
jm status --check      # exit 0
cmake -S . -B build && cmake --build build && ctest --test-dir build
```

and from Python:

```python
from stale.dsp import Fir
import numpy as np

f = Fir()
f.scale = 2.0
f.steps(np.ones(8, np.float32))          # [2.0, ...]: your kernel, intact
strided = np.zeros(16, np.float32)[::2]
f.steps(np.ones(8, np.float32), out=strided)
# TypeError: out must be a writable, C-contiguous ndarray of the output dtype
```

The strided `out=` that 0.33.14's binding silently ignored is now refused.

## For jm maintainers: it is also a regression gate

A fresh scaffold cannot show what goes wrong when a file an **older** jm
rendered meets a guard added later — it is rendered by the jm under test.
This project can. Everything each step prints is compared with
`upgrade.golden`, and the run first proves `tree/` is still the frozen tree
(its manifest's `jm_version` and every file's hash in `tree.sha256`).

A release that changes what upgrading prints *on purpose* regenerates the
golden in the same PR, and the diff is what gets reviewed:

```sh
JM_UPDATE_STALE_GOLDEN=1 make test-examples EXAMPLES_K=stale_project
```

Never regenerate `tree/`. The golden growing is the record of every guard
added since 0.33.14; if jm ever stops applying this project on purpose,
freeze a second one beside it and keep both
([gh-1443](https://github.com/just-buildit/just-makeit/issues/1443)).
