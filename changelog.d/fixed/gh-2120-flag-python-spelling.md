- **A manifest flag an older jm wrote as `"True"` is respelled by `jm upgrade`, and refused until it is (gh-2120).** Before gh-2046, a whole-manifest rewrite (`jm split-objects`, `jm migrate-to-fragments`) wrote `streamable = true` back as `streamable = "True"`, and nothing read that as true: a streamable producer lost `stream()` and `__iter__` from its `.pyi` and `_ext.c`, while `apply` and `status --check` exited 0 and `jm upgrade` said "already up to date". Now `jm upgrade` respells every `"True"` / `"False"` flag to the bool it was, at any schema, keeping comments. Every command refuses a flag holding any value but `true`, `false`, `"true"` or `"false"`, naming the key, and names `jm upgrade` for the old spelling. Every flag is read the same way, too: `process_global` accepted `"1"` and a property's `writable` accepted `"yes"`, and both are refused now, while a method's `bench = "false"` now opts out as `bench = false` does. And `"false"` is off wherever a flag is read: a property declared `writable = "false"` got a setter, and an init param declared `required = "false"` was required, because those readers tested the string for truth. The same holds for every boolean manifest key, not only the ones jm already treated as flags: a method's `nogil = "False"` loaded, was not respelled, and released the GIL, and `variable_output`, `single`, `borrow`, `strict`, a property's `getter_status`, a composer field's `bytes` and the rest read `"false"` as on. They are flags now, refused and respelled like the others.
